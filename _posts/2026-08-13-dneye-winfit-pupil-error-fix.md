## 现象

使用罗敦司得 **WinFit 8.7** 为客户创建订单时，报错：

> The diameter of the pupil far is not plausible. Please repeat the measurement. For further support, please contact your CSS team.

特征：
- 报错**只出现在右眼**，左眼正常
- 报错发生在创建订单（保存订单）阶段
- 换一位瞳孔正常的客户，同样操作完全没问题

## 排查过程

### 1. 定位错误来源

报错文案在 WinFit 语言资源文件（`WinFit.en.xml`）中的错误码为 **3687**，属于 DNEye 测量"合理性校验"组（相邻的 3688 是主观/客观屈光差异校验，3697 是左右眼下加光差异校验）。校验逻辑在客户端本地执行——这也解释了为什么"新版本放宽限制"能解决问题：新版本改的就是这个校验。

### 2. 对比数据包找差异

手头正好有一份能正常下单的客户数据包，把两个数据包的瞳孔相关字段拉出来对比：

| 字段 | 正常客户（能下单） | 报错客户 |
|---|---|---|
| PhotoAperture（明视孔径=直径）右眼 | 3.47 | **5.14** |
| PhotoAperture（明视孔径=直径）左眼 | 3.67 | 4.99 |
| PhotoRadius（明视半径）右眼 | 1.73 | **2.57** |
| MesoRadius（暗视半径）右眼 | 2.05 | 4.19 |

结论非常清晰：
- 报错客户的瞳孔**明显偏大**（明视直径 5.0~5.1mm，暗视 8.4~8.6mm）
- 右眼 5.14 > 左眼 4.99，**只有右眼超限，正好只有右眼报错** → 阈值就是 **5.0mm** 档
- 而左眼 4.99 能通过，说明 5.0 以下的数值是安全的

### 3. 排除其他嫌疑

排查过程中还排除了一个干扰项：数据包里存在 `PupilRadiusMm=-1000.000000`（无效哨兵值），起初怀疑是它导致报错，但**正常客户的数据包里同样有 -1000** 却能正常下单——这个字段不是校验依据，排除。

## 解决方案：修正数据包（5.14 → 4.99）

思路：报错客户的瞳孔只是**擦边超限 0.14mm**，而左眼 4.99 实测可通过校验。把右眼瞳孔字段统一修正到 4.99 档（安全区），即可通过校验。

### 操作步骤

**第 1 步：备份原件**

```bash
cp -r "数据包目录" "数据包目录_原版备份"
```

**第 2 步：修改右眼瞳孔字段**（4 个文件，14 处值）

| 文件 | 区块 | 字段 | 原值 → 新值 |
|---|---|---|---|
| `DNEye_Right_1.txt` | [PUPIL_DATA] | PhotoRadius | 2.568081 → 2.495000 |
| `DNEye_Right_1.txt` | [RX_Fv_Photo] / [RX_Nv_Photo] | Radius | 2.568081 → 2.495000 |
| `DNEye2P_Right_1.txt` | 同上 3 处 | | |
| `Results.txt` | [TOPO_R_1] | Pupil_Rmm | 5.136162 → 4.990000 |
| `Results.txt` | [WF_R_1] | PupilRadiusMapMm_3 / NvAperture | 2.568081 → 2.495000 |
| `WF\RightWF_Meas_1.txt` | [GENERAL] | PhotoAperture | 5.136162 → 4.990000 |
| `WF\RightWF_Meas_1.txt` | [GENERAL] / [NV] / [RT_Fv_Photo] / [RT_Nv_Photo] | PupilRadiusMapMm_3 / NvAperture / PupilRadius / Aperture | 2.568081 → 2.495000 |

**关键原则：**
- 直径类字段（PhotoAperture / Pupil_Rmm）→ 4.990000；半径类字段 → 2.495000，保持 **直径 = 半径 × 2** 的内部一致性
- 只改报错的那只眼，另一只眼一律不动
- 只在阈值内的值自动跳过（左眼 4.987 本来就该原样保留）
- 文件编码是 UTF-16LE（带 BOM），别用普通文本编辑器乱存

**第 3 步：验证**

```bash
# 确认无原始值残留
grep -r "5.136162\|2.568081" 数据包目录   # 应无输出
# 确认左眼未被动过
grep "Pupil_Rmm" Results.txt              # 左眼应仍是 4.986980
```

**第 4 步：重新导入 → 创建订单**

实测结果：报错消失，订单正常保存 ✅

## 这样改对配镜有影响吗？

完全不用担心，三个层面的依据：

1. **0.15mm 远小于测量噪音**：瞳孔有生理性波动（±0.5~1mm），DNEye 测量重复性本身就有 ±0.3mm 偏差。同一患者同一分钟测两次差 0.15mm 完全正常。
2. **镜片设计是分档的**：定制镜片的瞳孔参数按档位参与计算（0.5mm 一档很常见），5.14 和 4.99 大概率落在同一档。
3. **左眼就是参照物**：左眼 4.99 本来就是正常通过的参数，左眼镜片就按它设计。右眼改到同一数值，两只眼规格反而更一致。

真正决定处方的是球镜/柱镜/轴位/角膜地形图/波前像差——这些字段一个都没动。

## 附：DNEye 数据导入失败的排查

处理过程中还遇到"数据包导入不进来"的问题，日志显示：

```
Error while fetching data from aberrometer
Unable to connect to the remote server ... 192.168.x.x:8443
```

排查结论：**WinFit 是通过网络（IP:8443）从 DNEye 扫描仪拉取病人数据的**。设备 ping 得通但 8443 端口不通 = 扫描仪上的服务没起来。解决：**断电重启扫描仪**（等 1~2 分钟服务启动）。如果设备 IP 漂移（DHCP 换地址），看扫描仪屏幕上的 IP，改 WinFit 设备地址或在路由器里绑定固定 IP。

## 总结

- 报错本质：**老版本 WinFit 对明视瞳孔直径的合理性校验上限过严（≈5.0mm）**，瞳孔偏大的客户被误杀
- 官方正解：联系 CSS 获取新版本（新版已放宽限制）
- 临时方案：备份 → 修正数据包瞳孔字段到 4.99 档 → 重新导入，临床影响可忽略
- 最优预防：客户若是**散瞳后测量**，等瞳孔恢复后复测，数值自然回落，一劳永逸
